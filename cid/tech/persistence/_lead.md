## What the brief did not give me

Named, routed, not filled.

1. **No availability, uptime or data-loss tolerance anywhere in the brief.** A rollback
   procedure is normally written against one. The nearest thing is "shipped artifacts, not
   players". → **01** states the per-write tolerance it assumed; **03** states the
   per-migration one. Both are `[cid: decided]`.
2. **No session-locking position at all**, in a design with shared servers, 10–20 minute
   sessions and a single currency the brief itself calls the only thing worth cheating. →
   **02**, which must decide whether a lock exists before it decides its shape.
3. **No number behind "watch save size as areas accumulate."** → **01**, which must publish the
   bound and the headroom, not an adjective.
4. **No statement of what a save failure costs the player.** The shipped module already answers
   this and no key records the answer: a failed *read* at join latches `blockedSaves` for that
   Player and every later write returns false, so a whole session's progress is discarded
   silently. That is a defensible call and it is currently a comment in a Luau file rather than
   a decision anyone approved. → **01** declares it as data or overrules it with a reason.
5. **No policy for the next store bump.** `ArgaRuin_v2 → v3` was a wipe presented as a
   migration, correctly, because nothing had shipped. Nothing states what happens the second
   time, or what change forces a bump. → **03**.
6. **No owner for a save-failure log.** Warnings go to the server output and nowhere a human
   reads. Security names the same gap for detection, Analytics owns *what* to record and
   explicitly not the pipe. I do not open a second front: **01** names the emitted
   warning-per-failure as its only observability and states that the pipe is unowned.
   *Kind of work: server-side event transport and retention. Currently nobody's.*

## Why 3 sheets

My subject is one module's storage procedure plus two things that sit beside it and can be
decided independently of it. Sheet 01 is the module: the key string, the API, the retry
schedule, the failure behaviour, and the budget those retries are spent against — and the
budget belongs *with* the retry schedule rather than in its own sheet, because retries are the
only thing in this design that could threaten the budget, so setting one without the other is
setting neither. Sheet 02 is session locking, which is genuinely separable (it can be decided
`enabled: false` and nothing in 01 changes) and is a named gap in the brief. Sheet 03 is the
store's lifetime rather than one write: what forces a version bump, whether the old key is read
or abandoned, and what the procedure is. Partitioning gets no sheet — one player, one key, one
bounded payload, and inventing shards for a 24 KB value would be the failure this stage exists
to prevent.

**I am proposing three keys where my category lead expected one, and that is a deviation with a
reason.** `bridge/merge.mjs:135` makes two sheets proposing one key a hard error, and
`CLAUDE.md` requires every sheet to carry a manifest or declare it has no data form. Session
locking and store migration both have data forms, so folding them into `persistence` would
force one sheet holding three decisions, and splitting them without keys would produce two
prose sheets — the exact 78% defect this stage was rebuilt to remove. The split also buys
cross-key checks worth having: `sessionLock.enabled` constrains `persistence.writeApi`, and
`storeMigration.bumpTriggers` constrains `runtime.dataStoreName`. If the schema maintainer
prefers one key, the collapse is mechanical — the three become named top-level blocks of
`persistence` — and I would rather be overruled toward one key than pre-emptively bury two
decisions inside a third.

## Verification note

**Sheet 03 is the one most likely to be contradicted, and by wave 4.** Its central trigger is
that a change to `layout`'s composition invalidates every `state.cleared` index. Wave 4's
unreleased revision changes `depths.areas[].chunkCount` on all eight rows (4/5/7/10/15/19/26/30
against the merged 4/7/11/14/16/16/16/16) and the post-terminal bay from 30 to 47 chunks. If
that lands, it *is* a migration trigger by sheet 03's own rule, and `ArgaRuin_v3` needs a
fourth bump — which is `architect/01-runtime`'s field, not mine, and reaches it as a revision
request. Sheet 03 must be written so that the trigger fires rather than so that today's version
list stays true.

**Sheet 01 is second, and by two owners.** Its payload bound cites wave 4's 1,200 and 1,880
patch counts, which are unreleased; if RR-7's chunk-library breach forces area 7, 8 or the bay
to be resized, the bound moves again. And if Tech — Performance accepts the `clearTickRate`
0.04 request, nothing in sheet 01 changes numerically — the save interval is independent of the
tick — but a builder reading both will expect a link, so 01 should say in one line that there
is none.

**One contradiction found inside `architect/` while checking the shipped code, reported and not
fixed here.** `02-modules`'s `entitlements` acceptance criterion 3 reads: "`grep -rn 'owned'
game/src/server/Persistence.luau` returns nothing." It returns two matches — line 162 (a
comment) and line 164 (`owned = {}`) — and it must, because `07-wiring`'s `constructs` block
requires `persistence.defaultState()` to set "the five live fields to their empty forms —
patches {}, spawnPivot nil, **owned {}**, armState …". The criterion as written is
unsatisfiable against a sibling key in the same contract. `03-state-shape` criterion 8 greps
`state.owned` with the dot and passes correctly, so the fix is to narrow the `entitlements`
criterion to the same string. **The rule it is protecting — no purchase-derived value in a
payload — holds in the shipped file**: `save`'s payload literal is exactly the seven persisted
fields and `owned` is not among them.

Two further divergences between `game/src/server/Persistence.luau` and `architect/`, both
routed into sheet 01 rather than reported as defects: the module writes with `SetAsync` where
the platform docs recommend `UpdateAsync` for multi-server safety, and its `blockedSaves` latch
is a session-discarding behaviour that the module's own header calls "the one behaviour here
that is not in the state shape" — `wiring.onSave` describes only "a failure warns and the loop
continues; the next pass retries by existing", which is true of a write failure and silent
about the read-failure latch.

## Research owed

`must_verify` for this node is empty. The category lead and the orchestrator both required the
DataStore request budget to be derived against Roblox's real published limits or marked
`[playtest unknown]`. It is derived, from two independent fetches that agree.

**Fetched and usable by the writer:**

- `https://create.roblox.com/docs/cloud-services/data-stores/error-codes-and-limits` and its
  source `https://raw.githubusercontent.com/Roblox/creator-docs/main/content/en-us/cloud-services/data-stores/error-codes-and-limits.md`
  — fetched separately and cross-checked; the numbers agree. Server-level standard per minute:
  read `60 + numPlayers × 40`, write `60 + numPlayers × 40`, list `5 + numPlayers × 2`, remove
  `60 + numPlayers × 40`. Experience-level per minute: read `300 + concurrentUsers × 40`, write
  `300 + concurrentUsers × 20`, list `300 + concurrentUsers × 2`, remove
  `300 + concurrentUsers × 40`. Data: 50 characters for the store name, the key name and the
  scope; **4,194,304 characters per key**. Throughput per key: read 25 MB/min, **write 4
  MB/min**. Queue: **30 requests** per queue type, handled in order, dropped entirely beyond
  that. Storage: `500 MB + 1 MB × lifetime user count`. Error codes: 101–107 validation,
  301–306 queue throttle, 401–404 and 501–505 internal/transient, 509–513 permission and
  format.
- `https://create.roblox.com/docs/cloud-services/data-stores` — "The values you retrieve using
  `GetAsync()` sometimes can be out of sync with the backend due to the caching behavior", and
  the `SetAsync` vs `UpdateAsync` multi-server recommendation quoted in sheet 01's row.
- `https://create.roblox.com/docs/reference/engine/classes/DataStoreService` —
  `GetRequestBudgetForRequestType(requestType)` exists and returns the current budget;
  `Enum.DataStoreRequestType` members appearing in the samples are `StandardRead`,
  `StandardWrite`, `StandardList`, `StandardRemove`, `SetIncrementAsync`.
- `https://madstudioroblox.github.io/ProfileStore/` — session locking via `UpdateAsync`, a
  **300-second** default auto-save (up from ProfileService's 30), `MessagingService` for faster
  conflict resolution, and "exponential backoff, timeouts and cancel conditions".

**Fetched but incomplete, and the writer must treat it accordingly:**

- **The `BindToClose` 30-second window.** A direct fetch of
  `https://create.roblox.com/docs/reference/engine/classes/DataModel#BindToClose` returned the
  Studio note but not the timeout. A search against the same domain surfaced the doc's own
  sentence — "The experience server waits 30 seconds for all bound functions to stop running
  before it shuts down" — so I am citing it as `[research: url]` on that page with the fetch
  discrepancy recorded here. If a later reader needs it settled, the fetch that does it is the
  raw `creator-docs` markdown for `reference/engine/classes/DataModel.yaml`.
- **The `GetAsync` cache duration.** The docs confirm a cache exists but state no duration; the
  commonly-cited 4 seconds appears in no page I fetched. Any sheet needing it must mark it
  `[unverified]`. Nothing in my three sheets does: one read per join is far outside any cache
  window.
- **The per-key write cooldown.** Historically documented as 6 seconds; **it is not in the
  current limits page**, which lists a per-key *throughput* cap (4 MB/min) instead. Sheet 01
  must not cite a 6-second cooldown as sourced. At a 45 s interval it binds nothing either way.
- **`ProfileStore`'s steal timeout and crash behaviour.** The home page states the mechanism
  but not the numbers. Sheet 02 sets its own and marks them `[playtest unknown]` with a test
  range; the fetch that would settle the precedent is the library's API page.

**Not fetched, and named so nobody assumes otherwise:** nothing was fetched about the ~70%
mobile split (`cid/_state.md` already records it as uncorroborated) or about the 12–20 server
band. Neither reaches a number in my three sheets: every budget is computed at
`runtime.maxPlayers` 16, which is fixed place configuration, not an inference from either.
